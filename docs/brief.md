# BeoGeoQuest route tool — project brief

Источник: обсуждение в чате Claude (16.10.2026). Здесь зафиксированы решения и факты; всё, что помечено **[уточнить]**, ещё не подтверждено.

## 1. Игра

БеоГеоКвест — городской квест (организаторы GeoQuest). Типы заданий:

- **Классические КП** — кружок на бумажной карте + описание в Notion (адрес или ориентир, что искать, вопрос).
- **Загадки / полузагадки / задания** — на бумажных листках; отгадка = место в городе (адрес/объект), там вопрос.
- **Фотозадания** — либо прямые («фото с цветущим деревом»), либо фотозагадки (отгадка → место → фото).

Все точки обойти нельзя → выбираем маршрут, максимизирующий баллы.

### Правила (для нашей команды)

- **Баллы = `floor(номер / 10)`**, буквы в номере игнорируются: КП 64 → 6, 120 → 12, 12/13/14 → 1, 25А → 2. Для загадок так же (84 → 8). Отдельные задания без номера имеют баллы в тексте (фото 5, «Любовь это…» 6, «Моя чесма» 7, «В мире животных» 6, «Письмо себе» 7–9).
- **Категория: ПРО, пешком.** На карте: красный кружок — все категории, синий — Вело и ПРО, зелёный — только Вело. Нам доступны красные + синие. Отдельно в Notion бывают пометки «только для Вело» / «только для ПРО».
- **Длительность 9 часов строго.** Финиш до 19:30 (в игре 10.10.2026), можно опоздать до 30 мин, штраф −1 балл за минуту. Старт ≈ 10:30 **[уточнить]**.
- **Временные окна:** некоторые КП работают только в интервале (10.10: КП 99 и 120 — с 14 до 18).
- **Notion-страница с КП доступна только на старте**; во время игры организаторы её не правят (зачёркнутое и приписки в экспорте — правки до публикации). Импорт делается один раз, на старте, и входит в бюджет времени старта.
- **Команда до 4 человек, сейчас 2. Расходиться НЕЛЬЗЯ.**
- **Книжка ответов:** строки по номерам КП; для каждого — ответ и время (ЧЧ:ММ). **Без времени — 0 баллов.**
- Фотоответы сдаются на следующий день через форму; рисованные/ИИ-картинки не принимаются.
- Использование ИИ для решения загадок — **[уточнить по правилам]**.

- `osm-gazetteer.json` — справочник адресов OSM (16 148 адресов, 333 улицы, радиус 5 км) из выгрузки Geofabrik с данными на 15.10. Сверен со снятым через Overpass 16.10: расхождения — 5 адресов на краю круга, оценка geo по всем 34 КП совпадает.

**Бумажная карта — отрисовка OpenStreetMap** (16.10): названия улиц в Notion совпадают с OSM, в том числе там, где Google их уже переименовал (64 «Филипа Вишњића», 120 «Светог Стефана», 30 «Матија Хуђи»). Google к тому же плохо ищет сербскую кириллицу → источник адресов — OSM, Google для проверки ненадёжен.

Факты из Notion-экспорта (по парсеру, 16.10): 81 классический КП, из них 4 «только для Вело» (93, 94, 101, 110) и 1 «только для ПРО» (41) → 77 КП и 338 баллов по тексту Notion. **С учётом карты — 76 КП, 330 баллов**: КП 83 в Notion без пометки, а на карте это зелёная стрелка за краем (только Вело) — ранняя оценка «~331» учитывала именно это. Карта главнее Notion и по категории. **Адрес с номером дома — ровно у 34** (33 в заголовке + КП 120 в теле), остальные — ориентиры («Родник», «Фонтан», «Памятник») → основной источник координат — оцифровка карты, геокодинг вспомогательный. Загадки/задания дороже: в среднем ~8 баллов против ~4,3 у классики, суммарно ~180–190.

Известные ловушки парсинга Notion-markdown:
- первый жирный блок — дата `**10 октября 2026**`, не КП;
- разметка внутри слов: `Улица Филипа Виш**њ**ића98`;
- NBSP внутри адресов (в фикстуре 10.10 их нет — возможно, потерялись при сохранении; покрыто синтетическим тестом); смесь кириллицы и латиницы (`Пиjаца`, `Матje`);
- заголовки вида `**93 - Только для Вело**`, `**41 … - только для ПРО**`;
- зачёркнутый текст `~~…~~` (устаревшие вопросы);
- ссылки `maps.app.goo.gl` у некоторых КП;
- «+ Сделайте фото…» — доп. фото на КП;
- блок финиша `## **Финиш…**` с правилами опоздания.

Найдено при разработке парсера (все покрыты тестами `packages/ingest/test/fixture-2026-10-10.test.ts`): буквенные суффиксы (25А, 71Б), жирная строка внутри КП (`**Задание судьи**` у 99), КП без описания (79А), адрес в теле, а не в заголовке (120), окна времени только на карте, не в Notion (99, 120), римские цифры в адресах (`Краља Петра I 24`), диапазоны домов (`16-20`), адрес в скобках (`(Водна 16А)`), порядок КП не по номерам (120 раньше 110), опечатка «Сделйте».

## 2. Калибровка (прошлая игра 10.10)

- Итог: 16,62 км за 7:23 (шагомер, включает время до старта), 34 КП + 1 КП из фотозаданий.
- Основная трасса 12:20–18:36. Если старт ~10:30 — ~1 ч 50 мин ушло на старте (решение загадок и т.п.). **Сократить время старта — главный рычаг.**
- Из Хронологии: скорость на ходу ≈ 4,2 км/ч (нижняя оценка); длинные паузы 13:28 (45 мин), 15:08 (36 мин), 16:52 (22 мин) ≈ 100 мин; 11 коротких остановок по 4–8 мин.
- Стартовые параметры модели: **скорость 4,3 км/ч; КП 4–6 мин; загадка с поиском таблички ~8 мин; судья/видео дольше; отдых — отдельный блок 60–90 мин.**
- Следующие игры: трек пишет отдельный старый Android с GPSLogger (GPX 1.1, интервал 5 с, только GPS, distance filter 0, accuracy 40 м, GPS держать включённым).

## 3. Роли и устройства

- **Ульяна — iPhone — «секретарь»:** карточка КП (номер, баллы, полный текст задания, поле ответа, время), отметка «взято», гугл, задачи, пересчёт маршрута, экран переписывания в книжку. Вся техническая часть (скрипты, парсинг, разметка карты) — на ней.
- **Ира — Android — «штурман» и загадки:** следующие 3–4 точки плана, «вести» (в Organic Maps), «пропустить».
- **Загадки** решаются вместе на паузах; первая большая пауза — сессия по загадкам.
- **Старый Android в рюкзаке** — только GPSLogger.
- Ноутбук — только на старте (до выхода на трассу), потом остаётся в машине. В поле мобильный интернет есть.

## 4. Архитектура

Принцип: всё тяжёлое — на ноутбуке на старте; в поле телефоны автономны; бэкенд только синхронизирует состояние. Каждый слой деградирует: нет бэкенда → локально; нет PWA → KML + бумага.

```
[Старт, ноутбук]
 notion export ─► ingest ─┐
 фото карты ─► digitizer ─┼─► таблица КП ─► OSRM-матрица ─► OR-Tools ─► Problem + Plan
 загадки ─────────────────┘                                                  │
[Поле]                                                                       ▼
 iPhone (секретарь) ◄─ sync ─► backend (AWS) ◄─ sync ─► Android (штурман)
[После игры]  GPX + события «взято» ─► analysis ─► params.json
```

Компоненты (имена — предложение):

1. **core** (TS, `packages/core`, готово): типы и JSON-схемы (TypeBox → `schemas/*.v1.schema.json`).
   - `Kp`: id, номер, тип (classic/riddle/task/photo), баллы, цвет кружка, пометка категории (velo_only/pro_only), `eligible`, адрес, описание, зачёркнутое, доп. фото, ссылки, тип ответа, координаты + источник (geocode/map/manual/gmaps_link) и уверенность, окно времени, время на точке, исходный markdown. **Статуса в `Kp` нет** — состояние КП (взято/пропущено/ответ) вычисляется из `Event[]` (`projectState`, ещё не сделано).
   - `Problem`: точки (с `prize` = баллы × уверенность), матрица в **целых секундах**, старт, финиш, дедлайн, мягкий штраф, отдых, скорость — единый вход обоих солверов; все времена — секунды от `t0`.
   - `Plan`: упорядоченные остановки с временами прибытия/ухода, финиш, запас до дедлайна, выброшенные КП, хэш `Problem`.
   - `Event`: taken / skipped / solved / answer_changed / **reopened** (отмена ошибочного тапа); UUID, clientTs, deviceId, **seq** (монотонный на устройстве). Порядок — по (clientTs, deviceId, seq).
   - `Game` (`games/<дата>/game.json`): город, дата, часовой пояс, старт, финиш, категория, доступные цвета, **правило баллов**.
2. **ingest** (`packages/ingest`, готово): построчный парсер Notion-markdown. Выход — `games/<дата>/kps.json` (`Kp[]` + финиш) и `report.json` (статистика, проблемы с `файл:строка`). Проблемы делятся на критичные (id, баллы, категория — правим на старте) и косметику (не правим).
   - На старте: экспорт кладётся в `games/`, `./bgq init` раскладывает его в `games/<сегодня>/` (`notion-export.orig.md` — не трогать, `notion-export.md` — рабочая копия), берёт `game.json` прошлой игры (если прошлых нет — образец `games/_template/game.json`) с финишем из экспорта; `./bgq parse` пересчитывает при каждом сохранении.
   - В git из `games/` идёт только образец `games/_template/`; данные прошлых игр для тестов (экспорт, `game.json`, `overrides.yaml`) — в `fixtures/<дата>/`.
   - Ручные правки: структура (потерянный/ложный КП) — в рабочей копии `.md`; данные, которых нет в Notion (окна, цвет) — в `overrides.yaml` по id. После игры оба `.md` → `fixtures/<дата>/`, их дифф — новые тест-кейсы.
   - Запасной путь: текст, скопированный из браузера без разметки, тоже разбирается (покрыто тестом).
3. **geo** (`packages/geo`, готово): локальный справочник адресов OSM вместо онлайн-геокодера.
   - `./bgq osm <город>` — **накануне игры**: выгрузка OSM Сербии с Geofabrik (`serbia-latest.osm.pbf`, ~240 МБ, обновляется ежедневно, качается ~30 с; та же понадобится OSRM) → osmium вырезает 5 км вокруг центра города, улицы и все объекты с номером дома → справочник `games/osm/<город>.json` (сборка ~3 с, без сети). Нужен `osmium-tool` (brew).
   - Почему не Overpass (16.10): публичные серверы отвечали 502/504, зеркала — 500 даже на тривиальный запрос; данные те же (одна база OSM), но доступ ненадёжен.
   - `./bgq geo` — адресные КП последней игры → `games/<дата>/geo.json` (id → координаты, способ, уверенность, что совпало). Работает без сети, если справочник скачан.
   - Поиск: адрес → латиница без диакритики (сербская кириллица, русские буквы ы/й/…, латинские двойники) без слов «улица/трг/булевар/дом» → нечёткое совпадение с названиями улиц OSM (включая `name:sr-Latn`, `alt_name`, `old_name`) → номер дома: точно → диапазон «16-20» (только своя сторона улицы) → без буквы → соседний номер той же чётности → центр улицы. Уверенность = метод (0,95 … 0,2) × похожесть названия.
   - Результат на 10.10: все 34 адреса найдены, медиана ошибки 20 м, 90% ≤ 28 м, 33 из 34 ≤ 50 м (КП 35 — 63 м: большой участок, OSM и эталон указывают разные его места).
4. **digitizer** (`apps/digitizer` + `packages/georef`, MVP готов 16.10): `./bgq map` — веб-приложение на ноутбуке. Цель: <15 мин на всю разметку.
   - **Карту отсканировать нельзя**: её выдают на старте, в поле — только фото с телефона (карта на земле, «как получится ровно»), можно четвертями. Поэтому привязка — **по кружкам адресных КП**, чьи координаты уже нашёл geo (на 10.10 — 34 точки по всему городу): гомография (перспектива от съёмки под углом) + RANSAC (перепутанный номер, ошибка geo) + местная поправка по ближайшим опорным (сгибы, неровная земля). Каждое фото привязывается отдельно; КП на нескольких фото — берётся фото с лучшей общей точностью (на 10.10 это всегда общее фото; выигрыш от «лучшего локально» или усреднения — 1–2 м, не делаем).
   - Порядок: перетащить фото в окно (HEIC с iPhone → JPEG через `sips`) → клик по кружку → номер + Enter (цвет: ⌥1/⌥2/⌥3) → после 4 адресных КП привязка считается на лету; фиолетовые подсказки показывают, где по адресу должны быть остальные адресные КП (клик рядом подставляет номер) → панель точности (leave-one-out: медиана, 90%) и выбросы с кнопкой «не опорная».
   - Опорные — только КП, у которых geo нашёл дом по номеру (`exact`/`range`/`house_base`); «соседний дом» и «только улица» — нет.
   - **Карта главнее адреса (решено 16.10).** Организаторы рисуют кружок не всегда там, где адрес в Notion: 71Б — в Notion «Лале Станковића 1», на карте кружок у «1г», между ними ~200 м. Поэтому адрес нужен только как опорная точка для привязки фото; кружок, расходящийся с адресом, RANSAC исключает из опорных (панель: «кружок в N м от адреса — координаты берём с карты»), а **итоговые координаты всех отмеченных КП — с карты**.
   - Выход — `games/<дата>/map.json`: отметки (первоисточник) + привязка каждого фото + результат: id → координаты (`source: map`), цвет кружка, фото. Автосохранение на каждое изменение, атомарная запись.
   - Цвет кружка размечается вручную → категория (зелёный = только Вело). На 10.10: 63 красных, 13 синих, 1 зелёный (83).
   - **Стрелка за краем карты** (93, 94, 83, 101, 110 на 10.10) — отметка с переключателем «стрелка» (⌥4): даёт только цвет, в привязке не участвует, координаты — по адресу. Отмечать стрелку как кружок нельзя: её место на краю карты — направление, а не точка.
   - Дальше: автоподпись адресных КП по проекции, автопоиск кружков по цвету (OpenCV.js).
   - **Замер на 10.10 (16.10)**: карта на полу, iPhone, общее фото 5712×3213 + 4 четверти. Разметка 33 адресных КП на общем фото — **6 мин** (~11 с на кружок); с КП без адреса оценка ~14 мин — в бюджет 15 мин.
     Точность против эталона (каждый КП предсказан по остальным, 71Б исключён): общее фото — медиана 26 м, 90% ≤ 53 м; четверти — 25 / 49 м; среднее по всем 5 — 24 / 52 м. Ошибки по КП почти одинаковы на разных снимках → это «пол» ~25 м (кружки не точно на адресе + ошибка geo + эталон), крупнее снимок его не убирает. 25–50 м = 20–40 с пешком — для маршрута несущественно.
     **Вывод: в поле — одно общее фото**, четверти — только если на общем не читаются номера.
   - Фикстура: `fixtures/2026-10-10/map.json` (разметка 5 фото, без самих фото — тесту нужны только координаты кликов) → `apps/digitizer/test/fixture-2026-10-10.test.ts`: p90 ≤ 60 м на каждом фото, детерминизм, 71Б — с карты. Смоук на старом фото под углом с прикидочными кликами: 20 опорных, медиана 21 м, 90% ≤ 42 м.
4а. **table** (`packages/table`, готово 16.10): `./bgq table` → `games/<дата>/points.json` (схема `PointsFile` в core, `schemas/points.v1.schema.json`) — вход для маршрута и телефонов.
   - Записи — те же `Kp` (текст для карточки + координаты): `loc` по приоритету **ручная правка (`overrides.yaml`, `source: manual`) → кружок на карте → адрес (geo) → нет**; остальные найденные места — в `altLocs` (телефон покажет «по карте здесь, по адресу там»).
   - `mapColor` — с карты (override в `overrides.yaml` важнее); `eligible` — пометка Notion + цвет + категория игры.
   - Проблемы: критично — доступный КП без координат, номер на карте, которого нет в Notion; косметика — кружок дальше 60 м от точного адреса (только для доступных и только если адрес найден по номеру дома), доступный КП не на карте (координаты по адресу).
   - 10.10: 81 КП · доступно 76 · 330 баллов · координаты с карты у всех доступных · 0 критичных · 1 расхождение (71Б, 223 м).
   - Загадок пока нет: формат ввода не решён; они войдут в тот же `kps` с `kind: riddle`.
5. **routing**: локальный OSRM (Docker, extract Сербии с Geofabrik, профиль foot) → матрица. В поле для новых точек — OpenRouteService API; без сети — прямая × 1,3.
6. **solver**:
   - OR-Tools (Python, ноутбук): prize-collecting routing — disjunction со штрафом = баллы × уверенность, time dimension с service time и окнами, мягкий верхний предел на финише (−1 балл/мин, макс. 30 мин).
   - Эвристика (TS, телефон + Node для тестов): warm start от текущего плана → убрать взятое → жадная вставка по «баллы/минута» → 2-opt → выкидывание худших по «баллы/сэкономленное время», пока не уложимся.
7. **backend** (AWS, Terraform): Lambda Function URL (или HTTP API) + DynamoDB single-table (`game#id` → КП, план, события). Доступ по общему коду игры. События append-only, идемпотентная запись по UUID (conditional write).
8. **pwa** (Vite + TS, IndexedDB, service worker, очередь синхронизации с повторами):
   - **Секретарь:** карточка КП (ответ сохраняется при вводе; время ставится автоматически при «взято», правится вручную; фото для «перерисуйте знак»), список КП, загадки со статусами (разгадана ≠ взята), кнопка «пересчитать», индикатор запаса («финиш по плану 19:12, запас 18 мин»), чек-лист попутных фотозаданий, **экран переписывания** (по номерам, как в книжке; галочки «переписано»; подсветка пустых ответов/времени).
   - **Штурман:** следующие 3–4 точки, «вести» (`geo:` URI в Organic Maps), «пропустить» (→ авто-пересчёт).
   - Пересчёт запускает только секретарь (план не меняется у штурмана сам по себе), кроме «пропустить».
   - Ответ без времени не считается взятым.
9. **export**: KML/GPX для Organic Maps, подписи вида `92 · 9б · загадка`.
10. **analysis**: GPX трека + события → скорость, время на точке по типам, паузы → `params.json`.

Хранение ответов (телефон — основной носитель до финиша): IndexedDB сразу при вводе + бэкенд + копия у штурмана. PWA ставится на домашний экран iPhone (Safari может чистить хранилище сайтов). Пауэрбанк обязателен. Переписывание в книжку — партиями на больших паузах, на финише только остаток.

## 5. Дорожная карта (~10 недель, игра через 2–3 месяца)

## 6. Риски

- **Дубли** (двойной тап, повторный sync) → UUID события + conditional write; клиентская дедупликация.
- **Порядок событий** → состояние КП по clientTs последнего события, не по времени прихода.
- **Таймауты / нет сети** → sync никогда не блокирует UI; очередь с backoff; local-first.
- **Формат Notion изменится** → отчёт о нераспознанном + ручная правка; правило баллов в конфиге. Проверить формат заранее нельзя (страница — только на старте) → фикстуры прошлых игр, запасной путь «скопировать текст из браузера», на старте правим только критичное (id, баллы, категория), косметику — нет.
- **Плохое фото карты** (в поле, на земле, со сгибами) → снимать сверху, при дневном свете, без тени и вспышки; одного общего фото достаточно (четверти точность не добавляют, см. замер); привязка терпит перспективу и сгибы, выбросы показывает. Четверти — запасной вариант, если не читаются номера; на каждой нужно ≥ 6 адресных КП.
- **Нет справочника OSM на старте** → выгрузка и справочник готовятся накануне (`./bgq osm <город>`); без них `./bgq geo` не работает, адресные КП размечаются в digitizer вручную. Названия улиц в OSM могут измениться между печатью карты и выгрузкой — ищем и по `old_name`.
- **Время старта** — главный риск: если пайплайн >40 мин, он съедает выгоду.
- **iOS storage** → только с домашнего экрана + копии на бэкенде и у штурмана.
- **Батарея** → пауэрбанки.
